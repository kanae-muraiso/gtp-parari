# 受講者・保護者の入口

- 新規申込の確認メールに、申込情報をPARARIアカウントにつなぐ個別リンクを付ける。
- 成人は本人、未成年は保護者のメール確認済みアカウントで接続する。未成年本人の別メールがある場合は、本人専用リンクも送る。保護者と本人のリンクは別々に送付する。
- 教室の名簿登録が終わると、通常アカウントのHOMEと「所属先」に教室が表示される。確認待ちの間は、その状態を登録画面に表示する。
- `/my/classes/[school]` で開始日、開催予定、予約、欠席連絡、振替を確認・操作する。保護者が複数人を担当する場合は対象の受講者を選ぶ。
- 共通の `/my/calendar` でも所属先ごとのクラスカレンダーを開ける。
- 既存申込者への案内は、先生の「申込者・入会対応」から「アカウントの登録案内を送る」または「受講者ページの登録案内を送る」。初日の案内にも個別リンクを付ける。
- 主催者の事業作成・名簿編集・開催日編集は引き続きモニター限定。通常アカウントに管理権限を与えない。

## データと権限

作品のSSOT、保存形式、Editor/Viewer/Lexicalには変更しない。変更対象はクラスのAuth・API・DB・利用者向け画面。

`school_admission_cases` の本人・保護者アカウントと、在籍中の名簿を基にアクセスを許可する。呼び出し元の受講者IDを信用せず、APIとservice-role専用RPCで同じ関係を再確認する。通常アカウントからDB関数を直接実行できない。リンクを知るだけでは登録も個人情報の閲覧もできない。既に接続済みのアカウントを別IDに差し替えられない。

欠席連絡は `school_attendance` に保存。連絡による振替が許可された商品では未使用の振替権を一件だけ生成する。欠席によって空いた席はその日だけ予約可能にし、埋まった後の欠席取消・振替使用後の欠席取消を拒否する。入金済みの予約取消は教室への連絡を案内する。

`20261118095053_class_participant_accounts.sql` と `20261118101628_class_legacy_applicant_access.sql` は追加マイグレーション。旧形式の申込も、履歴の受講対象を推測で書き換えず、確認済み申込者と名簿との関連から接続する。未統合PR #212にも出欠テーブル案があるため、そちらを統合する際は同テーブルの重複作成を解消すること。通知・請求機能は取り込んでいない。

## 検証

- `test:class-participant-access`: 通常の本人・保護者、他児童・第三者の拒否、開始日前、月間カレンダー、予約、個別メールリンクを実APIの隔離アダプターで確認。
- `test:class-a-db`: PGliteで既存マイグレーションと今回のDDLを実行。成人の登録→名簿、兄弟と保護者、本人専用リンク、アカウント差替え拒否、欠席・振替・満席、退会・アーカイブ、DB権限を確認。
- `test:class-setup` / `test:participation-navigation` / typecheck / repository hygiene / build。
- ローカルbuildはSupabaseのビルド用ダミー値を使用。実メール配信、実利用者によるログイン、実決済はこの自動テストでは実行しない。

DB反映前後のSecurity Advisorは既存ERROR 1件・WARN 207件に増加なし。新テーブルのINFO「RLS有効・ポリシーなし」は、anon/authenticatedを拒否しservice_roleだけが操作する意図どおりの構成。
