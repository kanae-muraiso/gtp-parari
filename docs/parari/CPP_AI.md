## 情報保護と境界

1. サーバーがBearer tokenを `auth.getUser(token)` で検証する。未認証・期限切れ・匿名セッションは401。画面のログイン状態だけで認証を判断しない。
2. ユーザーIDはその認証結果からのみ取得。利用者がID・プロフィール・systemメッセージ・モデル設定をリクエストに指定すると400。許可ユーザーかどうかもサーバーで検証。
3. Supabaseの公開キーと本人JWTを利用し、RLSを維持する。service-roleキー・管理者による他人の代理閲覧は使わない。全プロフィールクエリに `eq("user_id", verifiedUserId)` を付ける。
4. 既存研究者プロフィールの存在と同窓会の参加設定を確認。同窓会のみの一般ユーザー、研究者プロフィールのない会社アカウントは対象外。プロフィールが下書きでも対象。
5. AIへ渡す列と出力項目を明示的に制限。学位・所属・立場、キーワード（20件）、学歴職歴（20件）、研究概要（3件）、自己アピールを上限付きで参照する。研究概要等は既存SSOTからテキストブロックだけを派生させる。SSOT原文をAPIレスポンスに返さない。
6. 連絡先専用テーブル、氏名・顔写真、研究歴の証明欄、PDF、論文リスト、他人のプロフィール、会社情報、管理用メモは取得しない。自由記述に本人が含めた機密情報までは除去できないため、送信対象の説明を画面に出す。
7. 参照情報はユーザーロールの資料として渡し、サーバーの指示と分離する。外部URL取得、ファイル読取、ツール実行、DB更新の機能はない。プロンプトによる原則遵守の完全保証はできないため、出力評価は別途必要。
8. 会話・プロフィールをDB、localStorage、sessionStorage、アプリログに保存しない。画面内のReact stateのみ。ログアウト・アカウント切替で子画面を破棄し、処理中のリクエストを中断する。外部APIには本人識別子を送信しない。
9. OpenAI Responses APIを固定のHTTPSエンドポイントで利用し、`store: false`、テレメトリー無効、自動再試行なし。これはOpenAI側のすべてのデータ保持がゼロであるという保証ではない。利用するOpenAI組織のデータ管理条件を確認する。
10. APIは `private, no-store`。生のエラー、プロバイダーのレスポンス、トークン、DBエラーを利用者やログへ露出しない。AIの回答はHTMLとして実行せずテキストとして表示する。

## 有効化（限定試行）

次のサーバー環境変数を設定する。いずれも `NEXT_PUBLIC_` を付けない。空欄があれば利用不可。既存の音声合成用 `OPENAI_API_KEY` は流用・自動参照しない。

| 変数 | 値 |
| --- | --- |
| `CPP_AI_ENABLED` | `true` のときのみ有効。停止時は削除または `false`。 |
| `CPP_AI_OPENAI_API_KEY` | CPP AI用OpenAIプロジェクトのAPIキー。GitやPR本文に記載しない。 |
| `CPP_AI_MODEL` | 運用側で確認したResponses API対応のテキストモデルID。固定のデフォルトは設けない。 |
| `CPP_AI_ALLOWED_USER_IDS` | 試行対象のSupabaseユーザーUUIDをカンマ区切り。空欄・未指定は全員利用不可。`*` の全員許可は未対応。 |

既存の `NEXT_PUBLIC_SUPABASE_URL` / `NEXT_PUBLIC_SUPABASE_ANON_KEY` も必要。CPP AIのためのDBマイグレーションや本番DB変更はない。料金の接続前に全研究者へ有料サービスを無条件開放しないよう、許可リストは必須としている。

モデル接続は `ai@7.0.136` / `@ai-sdk/openai@4.0.91` の同梱ドキュメント・型定義で確認し、バージョンを固定した。既存のOpenAI音声合成コードには変更を加えない。
