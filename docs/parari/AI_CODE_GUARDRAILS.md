# PARARI AI Code Guardrails

この文書は、PARARI開発でAIにコードを書かせる前に必ず読ませるための開発ガードレールである。

AIは、コードを提示する前に、この文書の内容を確認し、今回の修正がPARARIの原則に反していないことを明示しなければならない。

---

## 0. 最重要原則

PARARIにおいて、**SSOTが唯一の正本である**。

UI、Editor、Viewer、Lexical、React state、DB補助カラム、表示用データ、preview用データは、すべてSSOTから派生するものであり、SSOTの代わりになるものではない。

AIは、便利そう・簡単そう・実装しやすそうという理由で、この原則を変更してはならない。

---

## 1. 絶対原則

### 1.1 SSOTが唯一の正本

* 作品本文・構造・パネル情報の正本はSSOTである。
* EditorはSSOTを編集するためのUIである。
* ViewerはSSOTを読むためのUIである。
* Parser / Serializer / Renderer はSSOTを中心に動く。
* 保存形式を勝手に増やしてはならない。
* JSONモデルやLexical内部状態を、SSOTの代替正本にしてはならない。

---

### 1.2 Lexicalは本文装飾だけを扱う

Lexicalは、TEXT本文内のリッチテキスト編集のためだけに使う。

Lexicalが扱ってよいもの：

* 段落
* 改行
* 見出し
* 太字
* 赤字
* リンク
* 注釈リンク
* その他の本文内インライン装飾

Lexicalが扱ってはいけないもの：

* `[BOOK]`
* `[PAGE]`
* `[IMAGE]`
* `[NOTICE]`
* `[LIST]`
* `[BUTTON]`
* `[ACCORDION]`
* `[LINKS]`
* `[QA]`
* その他PARARIの構造タグ

PARARI構造タグをLexical Nodeとして管理してはならない。

---

### 1.3 構造タグはSSOTに残す

PARARIの構造は、必ずSSOT内のタグとして保持する。

AIは、構造タグをReact state、Lexical Node、別JSON、hidden metadataなどに移してはならない。

表示や編集のために一時的にparseしてもよいが、正本はSSOTである。

---

### 1.4 Editor都合で保存形式を変えない

Editorを作りやすくするために、保存形式を変更してはならない。

保存形式を変える必要がある場合は、コードを書く前に必ず停止し、理由・影響・移行方法を説明し、ユーザーの明示承認を得る。

---

### 1.5 旧BOOK互換を壊さない

PARARIには旧BOOK作品が存在する。

AIは、新PAGE仕様や新Panel Editor都合で、旧BOOK作品を壊してはならない。

特に以下を守る：

* 旧BOOK内の `[BOOK]` を正しく扱う。
* 旧BOOK内の `[PAGE] タイトル` を正しく扱う。
* 旧BOOK内の `[PAGE]` 直後の通常本文をPAGEINFOに飲み込ませない。
* 旧BOOK内の `[PAGE]` 直後の `[IMAGE] URL` は、legacy page image として扱う。
* 旧作品の画像・本文・ページ構造を新仕様の制限で消してはならない。
* 旧作品の閲覧が壊れる変更を、MVP都合で後回しにしてはならない。

---

### 1.6 無料／有料制限は保存SSOTを壊さない

無料ユーザーの制限や有料ユーザーの機能差は、原則として表示・操作・公開範囲の制限である。

AIは、無料ユーザーだからといってSSOTからタグ・本文・画像情報・パネル情報を削除してはならない。

保存されたSSOTは作者の作品正本であり、課金状態によって破壊してはならない。

---

### 1.7 公開ViewerにSSOTを露出しない

SSOTはPARARIの中核資産である。

公開Viewerでは、読者にSSOT原文を見せてはならない。
HTML、script、data属性、JSON埋め込みなどを通じて、読者側にSSOT原文を渡してはならない。

作者本人の編集画面ではSSOTを扱ってよいが、通常UIには不用意に出さない。
SSOT直接編集は、高度な編集・修復モードとして扱う。

---

## 2. PARARI編集画面の思想

PARARIの編集画面は、パネル管理画面ではない。
**読むように編集するワープロ**である。

守ること：

* VIEWは読者表示に近づける。
* EDITだけ操作UIを出す。
* TEXTはパネルだが、見た目は普通の本文として扱う。
* PAGEINFOのVIEWはタイトル中心にする。
* パネル種別やモード表示をVIEWに出しすぎない。
* 削除など危険操作はEDIT側に置く。
* ＋ボタンは本文にまとわりつかせない。
* Editorは作者が作品を直す場所であり、構造を見せびらかす場所ではない。

---

## 3. ルーティングの基本方針

### 3.1 外向き

* `/{username}/`
  作者紹介ページ、ホームページ入口、独自ドメイン入口。

* `/{username}/works`
  外向きの作者別作品リスト。

* `/{username}/w/{workId}`
  将来的な統一作品Viewer入口。
  PAGE / BOOK / 旧BOOK を内部で判定して表示する。

### 3.2 内向き

* `/my/works`
  作者本人の作品管理リスト。

* `/editor-v2/{workId}`
  新しい統一編集画面。

外向きの作品一覧と、自分用の管理リストを同じルートに混ぜてはならない。

---

## 4. コードを書く前に必ず確認すること

AIは、コードを提示する前に、必ず以下を短く明示する。

### 4.1 今回変更すること

今回の修正対象を明確にする。

例：

* TEXTパネルのEDITモードに削除ボタンを追加する。
* PAGEINFOのVIEW表示をタイトルだけにする。
* Viewerの統一入口を追加する。

### 4.2 今回変更しないこと

今回触らないものを明確にする。

例：

* SSOT保存形式は変更しない。
* parseBlocksの基本仕様は変更しない。
* Lexicalに構造タグを持たせない。
* 旧BOOK互換は変更しない。
* DBスキーマは変更しない。
* 公開ViewerにSSOTを露出しない。

### 4.3 影響範囲

今回の修正がどこに影響するかを明示する。

分類：

* Parser
* Serializer
* Editor
* Viewer
* RichText / Lexical
* DB
* Routing
* Payment
* Auth
* Legacy compatibility

### 4.4 SSOT原則チェック

以下を確認する。

* SSOTが唯一の正本であり続けるか。
* LexicalにPARARI構造タグを持たせていないか。
* Editor都合で保存形式を変えていないか。
* 旧BOOK互換を壊していないか。
* 公開ViewerにSSOTを露出していないか。
* 無料／有料制限で保存SSOTを破壊していないか。

この確認で不安がある場合、AIはコードを書かずに質問する。

---

## 5. AIが勝手にしてはいけないこと

AIは、ユーザーが明示的に依頼していない限り、以下をしてはならない。

* 保存形式を変える。
* DBスキーマを変える。
* 既存ルートを消す。
* 旧BOOK表示を後回しにする。
* 既存作品を読めなくする。
* Lexical側にPARARI構造を移す。
* SSOT以外の正本モデルを作る。
* ParserとViewerとEditorを同時に大きく変更する。
* 「一旦この方が簡単です」という理由で原則を曲げる。
* 「あとで戻せます」と言って暫定実装を正本化する。
* ユーザーが確認していない設計変更をコードに混ぜる。
* ついでに別の機能を直す。
* コードの一部だけを見て、全体方針を推測で変える。

---

## 6. 危険な兆候

AIが以下のような提案を始めた場合、作業を止める。

* 「今回は仮にJSONで持ちましょう」
* 「Lexical側に構造を持たせた方が自然です」
* 「旧作品は後で対応しましょう」
* 「SSOTはあとでserializeすれば大丈夫です」
* 「一旦この形式で保存しましょう」
* 「Viewer用に別の正本を作りましょう」
* 「この方が実装は簡単です」
* 「MVPなので互換性は後回しにしましょう」
* 「無料ユーザー用にSSOTから該当部分を削除しましょう」
* 「公開ViewerにSSOTを渡してクライアント側でparseしましょう」

PARARIでは、簡単な実装より、正本を壊さない実装を優先する。

---

## 7. コード提示時のルール

コードを提示する場合、AIは以下を守る。

### 7.1 ファイルパスを明記する

コードの先頭に対象ファイルを書く。

例：

```ts
// src/components/parari/...
```

### 7.2 JSTタイムスタンプを書く

例：

```ts
// 2026-06-30 07:45 JST
```

### 7.3 PART名を書く

例：

```ts
// PART: Quiet PAGEINFO viewer
```

### 7.4 コメントで目的を書く

例：

```ts
// コメント:
// - VIEWではPAGEタイトルだけを表示する
// - 公開範囲や表示モードは出さない
```

### 7.5 差し替え範囲を明確にする

AIは、以下のいずれかを必ず明示する。

* ファイル全体を差し替える。
* この関数だけ差し替える。
* このreturnだけ差し替える。
* この行の直後に追加する。
* このimportに追加する。

曖昧な「このあたりを直してください」は避ける。

---

## 8. 迷ったら止まる

AIは、以下の場合、コードを書かずに止まる。

* SSOT原則に反する可能性がある。
* 旧BOOK互換を壊す可能性がある。
* DBスキーマ変更が必要になる。
* ViewerとEditorの正本が分かれそうになる。
* 無料／有料制限が保存SSOTに影響しそうになる。
* 公開ViewerにSSOTが露出しそうになる。
* ユーザーの過去方針と矛盾する可能性がある。
* 影響範囲を把握できていない。
* 現在のファイル内容を確認できていない。

その場合、AIはまず選択肢を提示し、ユーザーに確認する。

---

## 9. 毎回のコード作成前テンプレート

AIは、コードを書く前に必ず以下の形式で確認する。

```text
🟩 WORK MODE 前確認

今回変更すること：
-

今回変更しないこと：
- SSOT保存形式は変更しない
- LexicalにPARARI構造タグを持たせない
- 旧BOOK互換を壊さない
- 公開ViewerにSSOTを露出しない
- 無料／有料制限で保存SSOTを破壊しない

影響範囲：
- Editor / Viewer / Parser / Serializer / DB / Routing / RichText / Lexical / Legacy compatibility など

SSOT原則チェック：
- SSOTは唯一の正本のまま
- Lexicalは本文装飾のみ
- 構造タグはSSOTに残す
- 保存SSOTを破壊しない
- 旧BOOK互換を壊さない
- 公開ViewerにSSOT原文を渡さない

この前提でコードを書きます。
```

この確認を省略してはならない。

## 10. 新しい開発スレッドの冒頭で使う短縮文

新しいチャットや開発スレッドでは、ユーザーは以下をAIに貼る。

```text
PARARI開発では、コードを書く前に必ず docs/parari/AI_CODE_GUARDRAILS.md の原則に従ってください。

特に守ること：
- SSOTが唯一の正本です。
- Lexicalは本文装飾だけを扱います。
- [PAGE] [BOOK] [IMAGE] などの構造タグをLexicalに持たせてはいけません。
- Editor都合で保存形式を変えてはいけません。
- 旧BOOK互換を壊してはいけません。
- 公開ViewerにSSOT原文を露出してはいけません。
- 無料／有料制限で保存SSOTを破壊してはいけません。

コードを書く前に必ず、
「今回変更すること」
「今回変更しないこと」
「影響範囲」
「SSOT原則チェック」
を先に出してください。
```

---

## 11. 最後の確認

AIは、PARARI開発において、自分の記憶や推測を正本にしてはならない。

正本は以下である。

1. 現在のリポジトリ内コード
2. ユーザーが明示した最新方針
3. この `AI_CODE_GUARDRAILS.md`
4. SSOT原則

AIは、過去の記憶や一般的な実装パターンよりも、PARARI固有の設計原則を優先する。

---

## Stripe / Payment Guardrail

AIは、Stripeのサンドボックス実装をもって「本番キーに入れ替えれば動く」と断言してはならない。

Stripe本番対応では、少なくとも以下を確認する。

- test mode と live mode の商品ID・価格IDは別である
- test mode と live mode のWebhook endpointは別である
- webhook signing secretも別である
- checkout session完了後にDBのplanが更新される
- subscription更新・解約・失敗イベントを処理する
- 本番環境変数が正しく設定されている
- 本番イベントログで成功を確認する

AIは、実際に本番環境で確認していない決済処理を「完成」と表現してはならない。
